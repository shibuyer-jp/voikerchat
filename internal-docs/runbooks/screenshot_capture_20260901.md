## 事前に頭に入れておく制約(読み飛ばさない)

- **このMac(x86_64シミュレータ)は `flutter run --release` / `--profile` が
  非対応**で、`flutter run` は **debug モードでしか起動できない**
  (DECISIONS.md 2026-07-28)。debug で問題ない:
- **DEBUG リボンは写り込まない**。`lib/main.dart` に
  `debugShowCheckedModeBanner: false` が恒久設定済み(DECISIONS.md 2026-07-28)。
- **統計画面(#7)は Premium 限定**。`GET /api/analytics` がサーバー側で
  `rate_limits.is_premium` を見て、false なら 403 を返す(`api/analytics.ts`)。
  → §B で本番DBを一時的に true にする。**撮影後に必ず戻す。**
- **介護・面接など #6 で見せたいシーンは Premium**(シーン14〜18=実用、
  9〜13=アニメ。無料は1〜8。`lib/services/scene_service.dart`)。非Premium
  ユーザーには鍵アイコン付きで一覧に表示される。
- **シミュレータのアカウントは実機と別の匿名ユーザー**になる。#5・#7 に必要な
  会話履歴・統計・バッジは **そのシミュレータ上で作らないと空**になる(§C)。
- 無料枠は10回/日(広告+5、上限20)。Premium は50回/日
  (`api/_constants.ts`)。**データ作りで枠を使い切ると撮影が止まる**ため、
  §B(Premium付与)→ §C(データ作り)→ §D以降(撮影)の順で行う。

## §A 必要なスクリーンショットのサイズ・枚数

> **最優先の方針: いま各ストアにアップロード済みのスクリーンショットと同じ
> 寸法・枚数で差し替える。** 既存分は受理実績があるため、寸法で迷ったら
> Console 上で現物の解像度を確認し、それに合わせる。以下は裏取り用。

### A-1. App Store Connect(iOS)

リポジトリの一次記録(DECISIONS.md 2026-07-29、実際に受理され公開済み):

| 枠 | 使用解像度(縦) | 枚数(現状) | 撮影に使うシミュレータ |
|---|---|---|---|
| iPhone 6.9インチ | **1320 × 2868** | 10枚 | **iPhone 16 Pro Max**(ネイティブ解像度が 1320×2868。無変換で提出可) |
| iPad 13インチ | **2064 × 2752** | 7枚 | **iPad Pro 13-inch (M4)**(ネイティブ 2064×2752。無変換で提出可) |

裏取り(Apple公式「Screenshot specifications」、確認日 2026-08-31):
- iPhone 6.9インチの受理解像度は 1320×2868 のほか **1260×2736** も受理される。
  どちらでも可。1320×2868 は公開済み実績があるためこれで統一する。
- iPad 13インチは **2064×2752**(縦)。
- 1ロケールあたり **1〜10枚**。iPhone は「app が iPhone で動くなら必須」、
  iPad は「app が iPad で動くなら必須」。6.5インチ枠しか無い画面から始めると
  寸法エラーになるため、**メディアマネージャーで 6.9インチ枠を明示的に展開**
  してからドラッグする(DECISIONS.md 2026-07-29 の罠)。

**変換ツール**(シミュレータ機種が上記と違う解像度になった場合のみ):
`shibuyer-ops/tools/appstore_screenshot_resize.py`
```bash
cd ~/<shibuyer-opsのパス>/shibuyer-ops && git pull
pip install pillow pillow-heif
python tools/appstore_screenshot_resize.py <入力フォルダ> <出力フォルダ>
```
`SKIP` と出たら未対応サイズ。iPhone 16 Pro Max / iPad Pro 13" で撮れば
そもそも変換不要。

- **未確認**: 現在 ASC に登録されている英語ロケール(en-US)のスクリーンショット枠が
  存在するか。primary は日本語で、2026-07-29 時点はスクリーンショットを日本語
  ロケールに入れて他ロケールへ自動継承させていた。§F の判断参照。

### A-2. Google Play Console(Android)

対象トラックのフォームファクタは「スマートフォン, タブレット, Chrome OS,
Android XR」。**必須はスマートフォン + タブレット**(Chrome OS / XR は任意、
今回は対象外でよい)。

裏取り(Google Play ヘルプ「Add preview assets」、確認日 2026-08-31):

| 種別 | 形式 | 解像度 | 枚数 |
|---|---|---|---|
| スマートフォン | PNG(24bit, α無し)or JPEG | 9:16 または 16:9。最小 **1080×1920**。最大辺は最小辺の2倍まで | 2〜8(4枚以上推奨) |
| タブレット(7"/10") | 同上 | 9:16 / 16:9。1080〜7680px | 4枚以上 |

- **アスペクト比の罠(未確認・要検証)**: Pixel 8 等の最近のエミュレータは
  1080×2400(2.22:1)で、「最大辺 ≤ 最小辺×2」を **超える**。生の
  スクリーンショットが Play Console の枠で弾かれる可能性がある。回避策:
  (a) エミュレータを 1080×1920(9:16)で作る、(b) 上下を 2160px 以内に
  トリミングする、(c) **既存アップロード済み Play スクリーンショットと同じ
  解像度**に合わせる(最も安全)。Play Console のアップロード画面は不適合
  ファイルに対して具体的な理由を表示するので、その場で確認できる。
- Android はシミュレータ弧のアーキ制約が無いため `flutter run`(debug で可、
  DEBUG リボンは出ない)で Android エミュレータを起動して撮る。
- **未確認**: 現在 Play Console にアップロード済みのスマートフォン用/タブレット用
  スクリーンショットの正確な解像度・枚数。撮影前に Play Console →
  ストアの掲載情報 → グラフィック で現物を開いて控えること。

## §B Premium 権限の一時付与と復旧(本番DB)

> **2026-09-01 追記(実施結果による訂正)**
> この手順で反映されるのは **ヘッダーの Pro バッジ・メッセージ上限(50)・
> Stats へのアクセス(403回避)まで**。**シーン一覧の鍵アイコンは外れない。**
> - 理由: シーンロック判定は RevenueCat SDK の Entitlement
>   (`Purchases.getCustomerInfo()`) のみを参照しており、Supabase の
>   `rate_limits.is_premium` を見ていない
>   (`internal-docs/reports/premium_state_mismatch_20260807.md`「1. シーンロック判定」)。
>   iPhone 16 Pro Max / iPad Pro 13-inch / Android エミュレータの3端末すべてで、
>   アプリ再起動・ホットリスタート・削除→再インストール後の初回起動のいずれでも
>   鍵は外れなかった。
> - したがって **#6(シーン一覧)を鍵なしで撮ることはこの方法では不可能**。
>   鍵なしが必要なら実購入フローを踏む必要がある(2026-09-01 は鍵ありで撮影した。
>   「## 実施記録」§3 参照)。
> - **ただし §B の実行は依然として必要**。#7 の Stats はこの手順で撮影可能になり、
>   `daily_limit = 50` は §C のデータ作り込み中の枠切れ防止に効く。
> - **§B-4 の復旧(撮影後に必ず元の値へ戻す)は従来どおり必須。**
> - **2026-09-02 追記**: コード調査により、この挙動は不具合ではなく仕様と
>   確定した(実購入フローでは正しく解錠される)。DECISIONS.md 2026-09-02 参照。

**#7(バッジ/統計)の撮影に必須。** DECISIONS.md 2026-08-01 に
「本番DBで `rate_limits.is_premium` を一時的に true にして実機確認し、
確認後は元に戻した」実績がある。同じことを SQL で行う。

> **本番DBへの変更。** `rate_limits.user_id` は UNIQUE 制約付きのため
> 対象は必ず1行。復旧に備えて変更前の値を必ず控える。

### B-1. 対象ユーザーの user_id を特定する

シミュレータでアプリを起動し(§C の起動手順)、**チャットを1通だけ送信**する。
送信時刻を覚えておく。Supabase SQL Editor で:

```sql
-- 直近の message_sent イベントから user_id を拾う。
-- 送信直後なら最上段が自分のシミュレータのユーザー。
select user_id, created_at, platform, locale
from public.usage_logs
where event = 'message_sent'
order by created_at desc
limit 5;
```

`platform='ios'` かつ送信時刻と一致する行の `user_id` を採用する
(複数端末が同時刻に動いていなければ最上段でよい)。迷ったら
`auth.users` の `last_sign_in_at desc` でも突き合わせる。

### B-2. 変更前の値を控える

```sql
select * from public.rate_limits where user_id = '<USER_ID>';
```

- **期待: 1行。** 0行なら user_id が誤り(§B-1 をやり直す)。
- 返ってきた行の **`is_premium` と `daily_limit`(あれば `used_today` も)を
  スクリーンショットまたはテキストで保存**する。§B-4 で使う。

### B-3. Premium を付与する

```sql
update public.rate_limits
set is_premium = true,
    daily_limit = 50            -- PREMIUM_DAILY_LIMIT(api/_constants.ts の現在値)
where user_id = '<USER_ID>';
```

- `daily_limit` も上げるのは、§C のデータ作りで無料枠(10)を使い切らない
  ため。`50` は `api/_constants.ts` の `PREMIUM_DAILY_LIMIT` の現在値。
  定義が変わっていたらそちらに合わせる。
- 反映はアプリ側のシーン一覧を開き直す/チャットを再度開くと効く
  (`onPremiumUnlocked` 経路、または画面再生成時)。

### B-4. 【撮影完了後・必須】元に戻す

すべての撮影が終わったら **必ず** 実行する(§完了チェックリスト参照):

```sql
update public.rate_limits
set is_premium = <B-2で控えた値>,
    daily_limit = <B-2で控えた値>
where user_id = '<USER_ID>';
```

戻したことを確認:
```sql
select user_id, is_premium, daily_limit from public.rate_limits where user_id = '<USER_ID>';
```

### 作り込む内容(操作量は推定。コード根拠を併記)

| 画面 | 必要なデータ | 具体的な操作(推定) | 根拠 |
|---|---|---|---|
| #5 リキャップ/言い直しシート | 同一シーンで **ユーザー発話3ターン以上** | 無料シーン1本に入り、短文でよいので3〜4往復。うち1〜2文はわざと助詞を間違えると「今日の言い直し」に補正が出て絵になる。→ 会話画面の「⋮」→ **Exit conversation** でシートが出る | `chat_screen.dart:1473` `_vocabSummaryMinUserTurns = 3`、シート表示は `_maybeShowVocabSummary`(1204行、exitConversation 経路) |
| #7 統計 | 会話セッションが1件以上(トークン数・学習時間・シーン進捗が埋まる) | #5 の会話で自動的に `conversation_sessions` / `usage_logs` に記録される。追加で2〜3シーン触ると「シーン別進捗」が複数行になり見栄えする | `api/analytics.ts` が `usage_logs`(event=message_sent)と `conversation_sessions` を集計 |
| #7 バッジ | 解除済みバッジが数個 + 進捗バー | 下表参照 | `lib/models/badge.dart` `BadgeCatalog` |

### バッジ(#7)をどこまで解除するか

バッジは「累計会話数(全セッションの総メッセージ数 ÷ 2)」等で解除される
(`badge_service.dart`)。**全9個の解除は非現実的**(`conversation_master_50`
は50会話=手入力100メッセージ)。撮影用には以下で十分:

| バッジ | 条件 | 現実的か |
|---|---|---|
| `first_step` | 累計1会話 | ◎ #5 の会話で自動解除 |
| `anime_explorer` | アニメシーン(9〜13)を1種類 | ◎ Premium 付与済みなのでアニメシーン1本を1往復 |
| `talkative_10` | 累計10会話(=20メッセージ) | △ 我慢すれば可。短文でよい |
| `basic_master` | 基本シーン8種すべて | △ 各シーン1メッセージずつでよい(8シーンに順に入って1往復) |
| `streak_3` / `_7` / `_30` | 連続学習日数 | ✗ 当日には作れない。進捗バー0で写る |
| `conversation_master_50` / `anime_master`(アニメ5種) | 高しきい値 | ✗ 進捗バーで写る |

→ **推奨: `first_step` + `anime_explorer`(+ 余力で `talkative_10`)を解除し、
残りは進捗バー表示のまま撮る。** 解除済み2〜3個 + 進捗バー6〜7個の
グリッドは訴求として十分成立する。バッジ画面(下タブ「Badges」)を
**開いた時点で自動的に解除判定が走る**(`badges_screen.dart:_load`)ため、
会話を作ってからバッジ画面を開けばよい。

- **注意**: バッジ解除状態は SharedPreferences(そのシミュレータ内)に保存
  される。シミュレータを消す/別のシミュレータに変えると作り直しになる。
  **#5・#7 は同じシミュレータで一気に撮る。**

### #6 の鍵アイコンをどうするか(Takatoh 判断)

- **鍵あり(非Premium状態で撮る)**: 介護・面接シーンに南京錠アイコンが付く。
  「Premium で開く上位コンテンツがある」と伝わり、深さ + アップセルを訴求できる。
- **鍵なし(Premium状態で撮る)**: 全シーンが解放されて見える。ラインナップの
  豊富さをそのまま見せられる。
- どちらでも規約上の問題は無い。**§B で Premium を付与した後は鍵が外れる**ため、
  鍵ありで撮りたいなら **#6 を §B の前に撮る**か、撮影順を工夫する。
  判断は Takatoh。過去のストア掲載文は「18 scenes ... caregiving, interviews」と
  ラインナップの広さを訴求しているので、**鍵なし(全解放)**の方が整合しやすい
  (推奨だが決定ではない)。

## §E キャプションの焼き込み

7本のキャプション(英語)は Store-Listing-Copy-v1.5.md「スクリーンショット構成」
の表にある。画像への焼き込み工程が必要だが、**使用する画像編集ツールは未確定**。

- ツール(Figma / Keynote / Preview のマークアップ / ImageMagick 等)が
  用意できるなら、各画像の上部または下部にキャプションを載せる。
- **ツールが無ければ、キャプション無しの素のスクリーンショットで提出しても
  ストア規約上は問題ない**(App Store・Google Play とも文字焼き込みは必須では
  ない)。ただし競合との差別化(「詰まっても逃げ道がある」訴求)が弱くなる。

  **#1・#2 を先頭**に置く原則は守る。
